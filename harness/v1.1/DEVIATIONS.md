# Deviation protocol and register — harness 1.1

The protocol is **unchanged** from `harness/DEVIATIONS.md` (1.0): same five classes E1 to E5, same
retry budget (3 gate retries, 2 review cycles), same impact rule. Read that file; it is not repeated
here.

Two additions for 1.1:

- **E6 Regression.** A change that makes a 1.0 behaviour differ. Declared by the reviewer or caught
  by gate G5/G6. Never acceptable silently: either the change is a deliberate, human-approved
  behaviour change recorded in the decisions log, or the task is rejected. This class exists because
  1.1 touches the pipeline that 1.0 shipped.
- **E7 Product.** A task that passes its tests but makes the tool worse to use: a control that is
  hard to find, a default that surprises, a message that does not say what to do next. Declared by
  the human at H6, H7 or H8, or by the reviewer on an ergonomics card (T26 to T29, T32). Resolution:
  a new card, size S, review full, generated by the orchestrator.

## Register

Format: one block per deviation, newest at the bottom. Status: open | accepted | rejected | resolved.

The 1.0 register (DEV-001 to DEV-008) is closed and stays in `harness/DEVIATIONS.md`. Nothing is
carried over.

```
### DEV-101
- class: E6 | task: Txx | contract: 1.1.0 | status: open
- raised by: reviewer | date: 2026-11-xx
- facts: <what regressed, quote the gate output or the baseline>
- assumption / proposal: <restore the 1.0 behaviour, or record the change as deliberate>
- decision: <filled by decider> | by: <reviewer / orchestrator / human>
- impact: <tasks affected, contract version bump>
```
