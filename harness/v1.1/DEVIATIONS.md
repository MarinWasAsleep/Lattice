# Deviation protocol and register — harness 1.1

The protocol is **unchanged** from `harness/DEVIATIONS.md` (1.0): same five classes E1 to E5, same
retry budget (3 gate retries, 2 review cycles), same impact rule. Read that file; it is not repeated
here.

Two additions for 1.1:

- **E6 Regression.** A change that makes a 1.0 behaviour differ. Declared by the reviewer or caught
  by gate G5/G6. Never acceptable silently: either the change is a deliberate, human-approved
  behaviour change recorded in the decisions log, or the task is rejected. This class exists because
  1.1 touches the pipeline that 1.0 shipped.
- **E7 Product.** A task that passes its tests but makes the tool worse to use: a control that is
  hard to find, a default that surprises, a message that does not say what to do next. Declared by
  the human at H6, H7 or H8, or by the reviewer on an ergonomics card (T26 to T29, T32). Resolution:
  a new card, size S, review full, generated by the orchestrator.

## Register

Format: one block per deviation, newest at the bottom. Status: open | accepted | rejected | resolved.

The 1.0 register (DEV-001 to DEV-008) is closed and stays in `harness/DEVIATIONS.md`. Nothing is
carried over.

```
### DEV-101
- class: E6 | task: Txx | contract: 1.1.0 | status: open
- raised by: reviewer | date: 2026-11-xx
- facts: <what regressed, quote the gate output or the baseline>
- assumption / proposal: <restore the 1.0 behaviour, or record the change as deliberate>
- decision: <filled by decider> | by: <reviewer / orchestrator / human>
- impact: <tasks affected, contract version bump>
```

### DEV-101
- class: E1 | task: T17 | contract: 1.1.0 | status: resolved
- raised by: coder | date: 2026-11-12
- facts: §16 typed `PaletteSpec.locked` as `list[int]` and said the locked indices are "seeded into
  the extraction result". At extraction time no palette exists yet, so there is nothing for an index
  to point into. The contract never said which palette the indices refer to.
- assumption / proposal: T17 shipped the field, its serialisation and the count validation
  (`len(locked) > extract_k` raises `ValueError`). The seeding itself was not implemented, because
  implementing it would have meant inventing the colour source. Proposal: either define `locked` as
  indices into the palette currently loaded in the UI, or change the type to a list of `#RRGGBB`
  colours.
- decision: **`locked` becomes `list[str]` of `#RRGGBB` colours**, seeded at the front of the
  extraction result. Indices into the UI palette were rejected because the render would then depend
  on hidden UI state: the same preset would render differently depending on what was on screen
  before, and the lock would silently do nothing in the CLI or a fresh session, breaking the
  invariant that a preset is a complete description of a render. Indices into `PaletteSpec.colors`
  were rejected as coherent but useless, since `colors` is empty or stale in the extracted workflow,
  which is exactly where locking matters. `locked` and `order` therefore address differently,
  colours and indices, each right for its job. | by: human
- impact: §16 amended in place, no version bump: no shipped preset used `locked`, so the reader
  change is a one-liner and no migration is needed. `core/pipeline.py` seeds the colours,
  `core/presets.py` reads them as strings, `ui/palette_panel.py` keys the lock on the colour instead
  of the index. T21's sixth accept item is now implemented.

### DEV-102
- class: E1 | task: T17 | contract: 1.1.0 | status: resolved
- raised by: coder | date: 2026-11-12
- facts: §13 puts `color_metric` on `PipelineSpec`, but the algorithm signature is
  `fn(img, palette, params)` and every algorithm calls `color.nearest_index(img, palette)` or
  `nearest_index_px(r, g, b, palette)` internally. The contract defines no path from the spec field
  to the kernel, and `resolve_params` rejects any parameter not declared in the algorithm's
  `params` tuple.
- assumption / proposal: T17 stores, validates and serialises `color_metric`; the field is inert
  until it is wired. Proposal: add `color_metric` to the algorithm call, either as a fourth
  positional argument or by injecting it into `params` after `resolve_params`. The second keeps the
  signature stable but needs a reserved key.
- decision: the second option, taken by T18 and T19. `render` converts the image and the palette to
  the metric's working space once, then sets `params["_color_metric"]` after `resolve_params`. The
  key is reserved: it starts with an underscore, so it cannot collide with a `ParamSpec` id, and
  `resolve_params` never sees it. Algorithms read it through `metric_of(params)`, which defaults to
  sRGB when the key is absent, so a direct call in a test still works. | by: orchestrator
- impact: none outstanding. A preset carrying `color_metric: "oklab"` now renders in Oklab.

### DEV-104
- class: E1 | task: T19 | contract: 1.1.0 | status: open
- raised by: coder | date: 2026-11-12
- facts: §14 gives each family its own `strength` semantics and requires `strength = 0` to equal
  `nearest_index` for all of them. For halftone the two cannot both hold: the card scales the spot
  threshold, and a threshold scaled to 0.5 produces two colours, not K. The same problem hits
  yliluoma (the card scales the candidate search) and dbs (the card scales the search radius):
  neither degenerates to the nearest-colour map at 0.
- assumption / proposal: those three families blend in colour space toward the nearest-colour map,
  `out = palette[algo] * s + palette[nearest] * (1 - s)`, then re-quantise. The invariant holds
  exactly, the control is smooth and monotone, and `strength = 1` is untouched. The cost is that
  the card's literal per-family wording is not implemented for these three. Proposal: rewrite §14
  to state the blend as the normative definition, and keep the per-family wording as a description
  of what `strength = 1` looks like.
- decision: | by:
- impact: none on the tests. A product decision if the literal per-family behaviour was intended.

### DEV-105
- class: E6 | task: T20 | contract: 1.1.0 | status: open
- raised by: coder | date: 2026-11-12
- facts: §15.1 gives one parameter block to `halftone_dots`, `halftone_squares` and
  `halftone_lines`, with `dot_shape: str = "round"`. Taken literally, all three algorithms default

  parameter, so nothing is lost. Proposal: write the per-algorithm default into §15.1.
- decision: | by:
- impact: none on the tests. G5 stays green because the defaults do not move.

### DEV-103
- class: E1 | task: T17 | contract: 1.1.0 | status: open
- raised by: coder | date: 2026-11-12
- facts: §13 gives an explicit formula for saturation in `[-1, 0]`
  (`out = lum + (c - lum) * (1 + saturation)`) and only the words "a lerp toward the fully saturated
  colour" for `[0, 1]`. A literal lerp toward the fully saturated colour normalises the chroma
  vector, which makes the control jump on nearly grey pixels: a pixel with a chroma of 0.05 reaches
  full saturation at `saturation = 0.05`.
- assumption / proposal: the same multiplicative form is used on both sides, so `saturation = 1`
  doubles the distance to the luminance. It is smooth, monotone, and satisfies every acceptance item
  of the card. Proposal: write the formula for `[0, 1]` into §13 so no coder has to choose.
- decision: | by:
- impact: none on the tests; a product decision if the harsher look was intended.

### DEV-106
- class: E1 | task: T23 | contract: 1.1.0 | status: open
- raised by: coder | date: 2026-11-12
- facts: §19 budgets "2048×2048, 16 colours, under 8 MB and under 5 s", and its rationale sentence
  speaks of "a 1024×1024 image with 16 colours". With one `<path>` per colour and horizontal run
  merging, the file size is driven by the number of runs, not by the number of colours, and the
  contract never says what the reference content is. Measured on this machine, 2048×2048:
  flat 16-colour blocks 0.49 MB in 0.30 s; a Floyd-Steinberg render of a gradient through `vga16`
  46.45 MB in 2.66 s; uniform random 16 colours 50.80 MB in 1.49 s. A dithered image has an average
  horizontal run length of about 1.07 pixels, so it produces about 3.9 M runs. The shortest run
  encoding SVG path syntax allows is `M0 0h1v1`, nine bytes, so the floor for that content is about
  35 MB. No path syntax reaches 8 MB on dithered content; the information content alone is 2 MB.
- assumption / proposal: T23 implements §19 as written, and the budget test is measured on flat,
  low-colour content, which is what a vector export is for. Proposal: state the reference content in
  §19. If it is flat artwork the budget holds as written; if it is a dithered render the budget must
  rise to about 50 MB, or the export must refuse above a size threshold instead of silently writing
  a 50 MB file.
- decision: | by:
- impact: T23's fourth accept item is met for low-entropy content only. No code change is needed
  until the contract names the reference content.

### DEV-107
- class: E1 | task: T25 | contract: 1.1.0 | status: resolved
- raised by: human | date: 2026-11-12
- facts: §21 said "No new dependency. ffmpeg is invoked as a subprocess if present", and the
  decisions log of 2026-11-11 repeated it. That rule makes the video export depend on a system
  install the project never declares: `pip install -r requirements.txt` produced an application
  whose `export_video` silently returned `False`, and the PyInstaller bundle advertised "no Python
  installation needed" while still needing ffmpeg on `PATH`. ffmpeg is a binary, not a Python
  package, so it cannot be pinned in `requirements.txt` as it stands.
- assumption / proposal: three ways to close the gap. `imageio-ffmpeg` ships a static ffmpeg inside
  its wheel, so the dependency becomes a normal `pip install`; `static-ffmpeg` downloads at install
  time, which is not reproducible; a documented system prerequisite plus an install script keeps the
  rule but leaves a manual step.
- decision: **`imageio-ffmpeg` becomes a project dependency**, pinned in `requirements.txt`.
  `export_video` resolves the binary through `imageio_ffmpeg.get_ffmpeg_exe()` and falls back to
  `shutil.which("ffmpeg")` when the dependency is absent, so a system ffmpeg still works. The
  PyInstaller bundle ships the binary through `--hidden-import` and `--collect-data`. PhotoCraft
  stays an integration, not a dependency: it is a separate application, detected at runtime.
  | by: human
- impact: §21 amended in place. `requirements.txt` gains one line; the wheel is 38.9 MB and carries
  ffmpeg 9.0.2 (essentials build, 105 MB unpacked). The onefile bundle went from 110 MB to 145.6 MB,
  measured. The "no new dependency" rule of 1.1 now reads "one new dependency, ffmpeg only". The
  absent-ffmpeg tests patch `export.video._resolve_ffmpeg` instead of `shutil.which`, because
  "absent" no longer means "not on PATH".

### DEV-108
- class: E1 | task: T24 | contract: 1.1.0 | status: resolved
- raised by: human | date: 2026-11-12
- facts: §20 says `separations = True` "additionally writes one greyscale PNG per ink ... computed
  from the CMYK conversion", and says nothing about the bleed or the crop marks. T24 computes the
  plates from the trim array, so a plate is `width × height` while the main PNG is
  `width + 2*bleed + 2*margin` by `height + 2*bleed + 2*margin`. Measured on the Game Boy render:
  the plates are 800×660, the print PNG is 940×800. A printer laying a plate over the print file
  would find it short by the bleed and the margin, so the two do not register.
- assumption / proposal: the plates describe the trim only, which is the area that carries ink; the
  bleed is a replication of the edge and the margin holds marks, neither of which is part of any ink
  plate. Proposal: state the reading in §20 rather than pad the plates.
- decision: **the plates stay trim-only, recorded as an assumed reading.** Lattice Dither targets
  digital art, where the print export is a convenience for a poster or a zine and not a production
  prepress workflow; padding the plates would add a second definition of the canvas for a use case
  the tool does not serve. | by: human
- impact: §20 amended in place, no version bump. No code change. A prepress user who needs
  plate-to-print registration would need a new card.
