# Deviation protocol and register — harness 1.1

The protocol is **unchanged** from `harness/DEVIATIONS.md` (1.0): same five classes E1 to E5, same
retry budget (3 gate retries, 2 review cycles), same impact rule. Read that file; it is not repeated
here.

Two additions for 1.1:

- **E6 Regression.** A change that makes a 1.0 behaviour differ. Declared by the reviewer or caught
  by gate G5/G6. Never acceptable silently: either the change is a deliberate, human-approved
  behaviour change recorded in the decisions log, or the task is rejected. This class exists because
  1.1 touches the pipeline that 1.0 shipped.
- **E7 Product.** A task that passes its tests but makes the tool worse to use: a control that is
  hard to find, a default that surprises, a message that does not say what to do next. Declared by
  the human at H6, H7 or H8, or by the reviewer on an ergonomics card (T26 to T29, T32). Resolution:
  a new card, size S, review full, generated by the orchestrator.

## Register

carried over.

### DEV-101
- class: E1 | task: T17 | contract: 1.1.0 | status: open
- raised by: coder | date: 2026-11-12
- facts: §16 types `PaletteSpec.locked` as `list[int]` and says the locked indices are "seeded into
  the extraction result". At extraction time no palette exists yet, so there is nothing for an index
  to point into. The contract never says which palette the indices refer to.
- assumption / proposal: T17 ships the field, its serialisation and the count validation

  implementing it would mean inventing the colour source. Proposal: either define `locked` as
  indices into the palette currently loaded in the UI, or change the type to a list of `#RRGGBB`
  colours.

- impact: T21 (palette authoring) cannot complete the lock feature until this is decided.

### DEV-102
- class: E1 | task: T17 | contract: 1.1.0 | status: resolved
- raised by: coder | date: 2026-11-12
- facts: §13 puts `color_metric` on `PipelineSpec`, but the algorithm signature is
  `fn(img, palette, params)` and every algorithm calls `color.nearest_index(img, palette)` or
  `nearest_index_px(r, g, b, palette)` internally. The contract defines no path from the spec field
  to the kernel, and `resolve_params` rejects any parameter not declared in the algorithm's
  `params` tuple.
- assumption / proposal: T17 stores, validates and serialises `color_metric`; the field is inert
  until it is wired. Proposal: add `color_metric` to the algorithm call, either as a fourth
  positional argument or by injecting it into `params` after `resolve_params`. The second keeps the
  signature stable but needs a reserved key.
- decision: the second option, taken by T18 and T19. `render` converts the image and the palette to
  the metric's working space once, then sets `params["_color_metric"]` after `resolve_params`. The
  key is reserved: it starts with an underscore, so it cannot collide with a `ParamSpec` id, and
  `resolve_params` never sees it. Algorithms read it through `metric_of(params)`, which defaults to
  sRGB when the key is absent, so a direct call in a test still works. | by: orchestrator
- impact: none outstanding. A preset carrying `color_metric: "oklab"` now renders in Oklab.

### DEV-104
- class: E1 | task: T19 | contract: 1.1.0 | status: open
- raised by: coder | date: 2026-11-12
- facts: §14 gives each family its own `strength` semantics and requires `strength = 0` to equal
  `nearest_index` for all of them. For halftone the two cannot both hold: the card scales the spot
  threshold, and a threshold scaled to 0.5 produces two colours, not K. The same problem hits
  yliluoma (the card scales the candidate search) and dbs (the card scales the search radius):
  neither degenerates to the nearest-colour map at 0.
- assumption / proposal: those three families blend in colour space toward the nearest-colour map,
  `out = palette[algo] * s + palette[nearest] * (1 - s)`, then re-quantise. The invariant holds
  exactly, the control is smooth and monotone, and `strength = 1` is untouched. The cost is that
  the card's literal per-family wording is not implemented for these three. Proposal: rewrite §14
  to state the blend as the normative definition, and keep the per-family wording as a description
  of what `strength = 1` looks like.
- decision: | by:
- impact: none on the tests. A product decision if the literal per-family behaviour was intended.

### DEV-103
- class: E1 | task: T17 | contract: 1.1.0 | status: open
- raised by: coder | date: 2026-11-12
- facts: §13 gives an explicit formula for saturation in `[-1, 0]`
  (`out = lum + (c - lum) * (1 + saturation)`) and only the words "a lerp toward the fully saturated
  colour" for `[0, 1]`. A literal lerp toward the fully saturated colour normalises the chroma
  vector, which makes the control jump on nearly grey pixels: a pixel with a chroma of 0.05 reaches
  full saturation at `saturation = 0.05`.
- assumption / proposal: the same multiplicative form is used on both sides, so `saturation = 1`
  doubles the distance to the luminance. It is smooth, monotone, and satisfies every acceptance item
  of the card. Proposal: write the formula for `[0, 1]` into §13 so no coder has to choose.
- decision: | by:
- impact: none on the tests; a product decision if the harsher look was intended.
